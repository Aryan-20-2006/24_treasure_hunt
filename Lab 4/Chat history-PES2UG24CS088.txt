● I read through game.py and haven't changed anything. Here's how it works, then
  the bugs and edge cases I found.

  How it works

  1. World generation — generate_world() (game.py:9-43 (game.py#L9-L43))

  - Grid: The map is a 20×15 list of lists (grid[row][col]). Every cell starts
    as WALL. Each tile is 40px.
  - Rooms: The code makes 8 attempts to place a random room, 3–6 tiles wide and
    3–5 tall.
    - The position range keeps a one-tile wall border around the map edge.
    - Each new room is grown by one tile on every side (inflate(2,2)) and
      checked against the rooms already placed. If it overlaps one, it's thrown
      away. So rooms always have at least one wall tile between them.
    - Accepted rooms are filled with FLOOR.
  - Corridors: Each room is joined to the next one in the list by an L-shaped,
    one-tile-wide corridor. It runs horizontally along room A's center row to
    room B's center column, then vertically to room B's center. Both ends are
    room centers, which are already floor, so every room ends up connected in a
    chain.
  - Items: The chest goes at the center of the last room and the key at the
    center of the second-to-last room. The player starts in rooms[0].

  2. How GameEngine, Player and the grid fit together

  - GameEngine owns everything: the pygame window, the clock, the grid, the
    player and the win/status state.
    - reset() builds a new world and puts the player at the top-left tile of the
      start room, 6px in from the corner. A 28px sprite at that spot sits
      exactly in the middle of the tile.
    - run() is a standard loop: handle_events → update → draw → tick(60).
  - Player doesn't store the grid. It's only a pixel-space Rect plus a has_key
    flag.
    - The engine passes the grid into move() each frame. Collision is the only
      place the player reads the grid.
    - The engine owns pickups and changes the grid there.
  - The grid is the single source of truth, for both drawing and collision.
    Pixel coordinates convert to tile coordinates with // TILE.

  3. Movement and collision (game.py:58-73 (game.py#L58-L73))

  - Input: move() reads the held arrow or WASD keys into dx and dy (±3px per
    frame).
  - Axis-separated moves: It calls _try_move twice, once for x and once for y.
    That's why you slide along a wall when moving diagonally into it instead of
    stopping dead.
  - The collision check: _try_move works out the new rect and tests its four
    corner pixels (using right-1 and bottom-1 so the check stays inside the
    rect). If any corner lands in a WALL tile or outside the grid, the whole
    step is rejected. Otherwise the new rect is accepted.
  - Chests and keys are walkable: Only WALL blocks movement.
  - No tunneling: At 3px per frame the player can't skip past a 40px wall.

  4. Key and chest pickup (game.py:112-126 (game.py#L112-L126))

  - After moving, update() finds the tile under the player's center point.
  - Key: Stepping on the KEY tile sets has_key, turns that tile back into FLOOR
    (so it disappears) and updates the status text.
  - Chest: Stepping on the CHEST tile while holding the key sets won = True.
    After that, update() returns early, so the player freezes and the win
    overlay is drawn.
  - Restart: Pressing R at any time calls reset(), which creates a new world and
    a new Player, so has_key is cleared too.

  Bugs and edge cases

  Real bugs
  1. Unwinnable maps. Chest and key are only placed if at least 2 rooms were
     accepted (game.py:37 (game.py#L37)). If 7 of the 8 attempts overlap, you
     get one room with no key and no chest, but the status still says "Find the
     KEY, then the CHEST!". Nothing tells the player; they have to guess to
     press R.
  2. Dead fallback code. The first room attempt can never overlap anything, so
     rooms is never empty and start is never None. The else branch at
     game.py:100-101 (game.py#L100-L101) is unreachable. If it ever did run,
     (46, 46) would be inside a wall tile and the player would be stuck.

  Gameplay and feel
  3. Key can be in the start room. With exactly 2 rooms, rooms[-2] is rooms[0],
  so the key spawns in the room you start in. That's not a crash, but it makes
  that map trivial.
  4. Can't touch walls. When a step would enter a wall, _try_move rejects the
  whole step instead of moving up to the wall. Positions only change in steps of
  3 and walls sit on multiples of 40, so the player often stops 1–2px short of
  a wall.
  5. Diagonal movement is faster. Moving diagonally goes about 1.41× faster,
  since you get 3px on each axis.
  6. Opposite keys don't cancel. Holding left and right moves you right; holding
  up and down moves you down. The later if wins.
  7. Corridor entrances need exact alignment. A corridor is 40px wide and the
  player is 28px, so the player has to be within 12px of lined up to enter one.
  There's no corner-assist, so turning into a corridor can feel sticky.
  8. No feedback at the chest without the key. Walking onto the chest without
  the key does nothing and the status text doesn't change.
  9. Movement depends on frame rate. Speed is measured per frame, not per
  second, so if the game drops below 60 FPS the player slows down.

  Cosmetic or harmless
  10. Chained corridors look messy. Rooms are linked in the order they were
  created, not by distance. Corridors can be long, cut through other rooms or
  run alongside them, which makes odd merged shapes.
  11. Extra frame on quit. After a QUIT event, update() and draw() still run
  once more before the loop exits. This is harmless.
  12. Redundant bounds checks. The checks at game.py:71 (game.py#L71) and
  game.py:118 (game.py#L118) can never fail, because the border is always wall.
  They're fine to keep as safety.

  If you want to fix any of these, #1 matters most. The simplest fix is to
  regenerate the map until it has at least 2 rooms (or 3, which also fixes #3).

  class Guard:
      def __init__(self, a, b):
          self.rect = pygame.Rect(a[0], a[1], 28, 28)
          self.a, self.b = a, b
          self.target = b
          self.color = (40,180,90)

      def update(self):
          tx, ty = self.target
          dx = max(-GUARD_SPEED, min(GUARD_SPEED, tx - self.rect.x))
          dy = max(-GUARD_SPEED, min(GUARD_SPEED, ty - self.rect.y))
          self.rect.move_ip(dx, dy)
          if self.rect.topleft == self.target:
              self.target = self.a if self.target == self.b else self.b

      def draw(self, screen):
          pygame.draw.rect(screen, self.color, self.rect, border_radius=6)
  - Movement: Each frame the guard steps toward its current target point, by at
    most GUARD_SPEED pixels on each axis. That limit also means it can't
    overshoot the target.
  - Turning around: When it reaches the target exactly, it switches to the other
    point.
  - Separate from Player: It has no keyboard input and no grid collision. It
    doesn't need collision because the lane is always clear.
  - Look: It's a green rounded square. The player is a blue circle, spikes are
    red, pits are black, and the key and chest are yellow and gold, so it's easy
    to tell apart.
